Neovim Config

A modular Neovim configuration built around lazy.nvim, with a minimal bootstrap, plugin specifications organized by purpose, and a clear separation between:

  • core modules loaded immediately
  • plugins loaded by lazy.nvim
  • development tools managed by Mason
  • Explicitly declared formatter and linter

The goal is to keep a simple entry point, small modules, and a predictable way to extend the configuration.

Bootstrap and Structure

The entrypoint is init.lua:

  1. load myconf.core
  2. bootstrap of lazy.nvim and import of plugin specs
  3. apply theme and palette
  4. activate the custom winbar

In practice the flow is this:

init.lua
├── myconf.core
│   ├── editor/options.lua
│   ├── ui/tabline.lua
│   ├── mappings/*
│   ├── cmd/*
│   └── events/*
├── myconf.lazy
│   ├── bootstrap lazy.nvim
│   ├── import myconf.plugins
│   └── import myconf.plugins.lsp
├── myconf.theme.theme
└── myconf.ui.winbar

The main directories are:

  • lua/configuration.lua: toggle and global setup values
  • lua/myconf/core: options, mappings, commands and autocmd loaded eagerly
  • lua/myconf/plugins: General spec plugins for lazy.nvim
  • lua/myconf/plugins/lsp: Spec plugins for LSP and Mason
  • lua/myconf/theme: palette, theme and color utilities
  • lua/myconf/ui: components Custom UI outside the plugins
  • lazy-lock.json: pinned plugin versions

How Modules Are Loaded

core modules

core modules are discovered automatically by lua/myconf/core/utils/modules.lua; they do not need to be registered one by one.

This applies to:

  • lua/myconf/core/mappings
  • lua/myconf/core/cmd
  • lua/myconf/core/events

Every .lua file in those directories, except init.lua, is loaded automatically. If a module exports:

  • If it exports a table with setup(), that method is called.
  • If it exports a function, that function is called directly.

Adding a mapping or command usually only requires a new file in the appropriate directory.

Plugin with lazy.nvim

The lazy.nvim bootstrap lives in lua/myconf/lazy.lua. On the first launch:

  • If lazy.nvim is missing from stdpath("data"), it is cloned with Git.
  • The runtime path is updated.
  • lazy.nvim imports plugin specifications from myconf.plugins and myconf.plugins.lsp.

Each file in those directories returns a valid lazy.nvim plugin specification. The conventions are:

  • one file per plugin or per small area
  • event, ft, cmd or keys for lazy-loading when possible
  • dependencies declared locally in the spec
  • keep opts or config in the plugin specification file

Examples:

  • lua/myconf/plugins/telescope.lua
  • lua/myconf/plugins/nvim-cmp.lua
  • lua/myconf/plugins/lsp/lspconfig.lua

Key Modules

Global Config

lua/configuration.lua is the right place for:

  • toggle UI like winbar, smooth scrolling and backdrop
  • small but global values such as the maximum number of splits
  • choice of theme (dark or light)
  • override external binaries in conf.external

The ui.theme() function also reads NVIM_THEME, so you can override the theme from the shell:

NVIM_THEME=light nvim

External binaries can also be overridden with optional environment variables:

NVIM_ZOXIDE_BIN=/custom/bin/zoxide \
NVIM_SIOYEK_BIN=/custom/bin/sioyek \
nvim

In the current TeX workflow, Sioyek is used by vimtex as a viewer. texlab remains separate and is not used as entrypoint for preview or forward search.

Core

  • lua/myconf/core/editor/options.lua: basic options, filetype indentation, text wrapping, scrolloff dynamic
  • lua/myconf/core/mappings: leader, base shortcut, split navigation, terminal mapping
  • lua/myconf/core/cmd: custom commands like :ConfigEdit, :ReloadConfig, :CodexHere, :Finder, :Z
  • lua/myconf/core/events: general autocmd and backdrop for some floating UIs

UI And Theme

  • lua/myconf/plugins/colorscheme.lua: setup of tokyonight with custom palette
  • lua/myconf/theme/palette.lua: converts the external palette into values used by the theme
  • lua/myconf/ui/winbar.lua: custom winbar with filename, icons and breadcrumbs LSP via nvim-navic
  • lua/myconf/plugins/lualine.lua: statusline

Navigation And Search

  • lua/myconf/plugins/telescope.lua: main pickers, file_browser, zoxide, fzf
  • lua/myconf/plugins/fzf.lua: fzf-lua as a quick alternative
  • lua/myconf/plugins/nvim-tree.lua: side explorer
  • lua/myconf/plugins/smart-splits.lua: resize, swap buffer and integration with WezTerm

Editing

  • lua/myconf/plugins/treesitter.lua: parser, highlighting, incremental selection
  • after/queries/ecma/textobjects.scm: custom Treesitter query for textobject on JS/TS properties
  • lua/myconf/plugins/nvim-cmp.lua: completion and snippet
  • lua/myconf/plugins/conform.lua: filetype formatter
  • lua/myconf/plugins/nvim-lint.lua: linter on autocmd

LSP

  • lua/myconf/plugins/lsp/mason.lua: installation of tools and language servers
  • lua/myconf/plugins/lsp/lspconfig.lua: server enable, override and keymap on LspAttach

How lazy.nvim Works in This Setup

Here lazy.nvim does three things:

  1. plugin manager bootstrap
  2. import of all plugin specs
  3. actual lazy-loading via event, ft, cmd and keys

Important setup choices:

  • checker.enabled = true: Check for updates plugins
  • change_detection.notify = false: no spam by notifications when you edit config files
  • lazy-lock.json: pin installed versions

Useful commands:

  • :Lazy: main panel
  • :Lazy sync: Install/update and realign plugins
  • :Lazy restore: Reset lockfile versions

Adding a Plugin

To add a new plugin:

  1. create a file in lua/myconf/plugins/ or lua/myconf/plugins/lsp/
  2. return a spec lazy.nvim
  3. always prefer a lazy trigger (event, ft, cmd, keys) if the plugin does not It is used for startup
  4. run :Lazy sync

Minimal example:

return {
   "folke/which-key.nvim",
   event = "VeryLazy",
   opts = {},
}

If a change is just runtime UI/theme you can often use :ReloadConfig; if you touch plugin spec, dependencies or bootstrap it is better to do :Lazy sync or restart Neovim.

LSP, Mason, Formatters, and Linters

LSP

This setup separates tool installation from language-server activation:

  • Mason installs servers and tools
  • lspconfig decides which servers to really enable and with which overrides

In lua/myconf/plugins/lsp/lspconfig.lua:

  • servers are listed in servers
  • the exceptions are in server_overrides
  • all receive the capabilities of cmp-nvim-lsp
  • LSP keymaps are registered to LspAttach, then they are buffer-local

Add a New Language Server

Recommended flow:

  1. add the package in ensure_installed of mason-lspconfig if you want to auto-install it
  2. add the server name to the servers list
  3. create an override in server_overrides only if needed filetypes, cmd, settings or root_markers

Conceptual example:

-- mason.lua
ensure_installed = {
   "ts_ls",
}

-- lspconfig.lua
local servers = {
   "ts_ls",
}

local server_overrides = {
   ts_ls = {
      settings = {
         -- ...
      },
   },
}

The automatic_enable = false setting in mason_lspconfig.setup() is intentional. Servers are activated in lspconfig.lua, not by Mason.

Formatter

Formatting is handled by conform.nvim in lua/myconf/plugins/conform.lua.

Setup Pattern:

  • map filetype -> formatter to formatters_by_ft
  • any custom formatters are defined in formatters
  • manual formatting on <leader>fi
  • lsp_fallback = true provides a fallback to LSP formatting.

To add a formatter:

  1. add the tool to mason-tool-installer if you want auto-install it
  2. add the filetype -> formatter pair in formatters_by_ft
  3. if you need custom binary or custom arguments, define it in formatters

Linter

Linting is handled by nvim-lint in lua/myconf/plugins/nvim-lint.lua.

Setup Pattern:

  • map filetype -> linter to linters_by_ft
  • try_lint() runs on BufEnter, BufWritePost, InsertLeave
  • manual trigger on <leader>ll

To add a linter:

  1. add the tool to mason-tool-installer if it needs to be self-installed
  2. record the filetype in linters_by_ft

Useful Configuration Commands

  • :ConfigEdit: opens a config file with selector
  • :ConfigVars: opens lua/configuration.lua
  • :ReloadConfig: Reload theme and light modules
  • :Lazy: plugin panel
  • :Mason: tool/LSP panel

Note About Mason

Mason installs some of the servers and tools declared in the repository, but these are distinct from the requirements for starting the basic configuration.

In this setup, at least:

  • LSPs installed by Mason: html, cssls, svelte, lua_ls, graphql, emmet_ls, prismals, pyright, gopls, jdtls, clangd, texlab
  • tools: prettier, stylua, isort, black, pylint, eslint_d, clang-format, latexindent

These tools support the development workflow, but not all are required just to start Neovim. Some also require external runtimes:

  • jdtls requires python3 and a java runtime; this setup requires at least Java 21
  • prettier and eslint_d require node
  • latexindent is installed by Mason, and this setup passes ~/.config/latexindent/config.yaml to it

Project Conventions

When extending this configuration, follow these conventions:

  • a plugin file = a clear responsibility
  • small global toggles in lua/configuration.lua, not scattered throughout the plugins
  • core modules without hidden side effects: better setup() explicit
  • use lazy-loading for anything that is not needed at startup
  • avoid absolute platform paths unless strictly necessary
  • If you add a feature with external dependencies, document it here

Quick Bootstrap

On a new machine, the minimal setup is:

  1. install the hard requirements in the section above
  2. place this config in ~/.config/nvim
  3. verify that ~/.config/theme/colors.lua exists
  4. open nvim
  5. run :Lazy sync
  6. open :Mason and check that the required servers and tools are installed
